# IncBlog audit rollout

IncBlog remains an Express/EJS application with Sequelize. The local changes address signing secrets, stored XSS and rendering, OAuth and browser writes, mail verification and consent, private media, database TLS and startup, public query performance, and crawler metadata. Production and the account recovery investigation remain separate from the local test results.

## Before an approved deployment

1. **Preserve data.** Confirm which database and storage the live app uses. Take verified database and media backups. Rehearse on copies and preserve the original user IDs, blog usernames, and post slugs. Review legacy Google links under the ownership procedure in the README. The incident involving the original account still needs production evidence.
2. **Prepare the database.** Use `MIGRATION_DATABASE_URL` with the migration role, `DATABASE_URL` with the runtime role, and `PG_CA_FILE` if the provider requires a private CA. Run `npm run db:prepare` on the approved target through migration 5. Before rollout, check for duplicate per-author current slugs, duplicate non-null Google subjects, and duplicate subscriber addresses within a blog. Migration 5 keeps current slugs and fails on conflicts instead of silently renaming posts. Renames recorded after this migration can redirect. Historical names that were already lost cannot be inferred by migration. See [media and database rollout](MEDIA-AND-DATABASE-ROLLOUT.md) for runtime grants and preserving a previously seeded demo account while disabling sign-in.
3. **Cut over private media.** Reconcile the legacy inventory first. Keep original keys and aliases as described in the media guide. Disable R2's public development URL and any direct public custom domains or Workers. Purge old CDN URLs and bypass caching on the gated app route. Check that old private endpoints are closed and that publicly referenced originals, variants, and legacy images load without authentication.
4. **Rotate signing secrets.** Generate separate 32-byte random lowercase hexadecimal values for `JWT_SECRET` and `SESSION_SECRET`. Store them in the hosting secret store, use the same pair across replicas, and retire instances using the old pair. Existing login and session cookies become invalid. Set a bare HTTPS `BASE_URL`, such as the approved production origin, and configure `TRUSTED_PROXIES` for the actual TLS terminator.
5. **Configure Google and mail.** In Google Cloud Console, set the OAuth web client's redirect URI to `<BASE_URL>/auth/google/callback`. Keep Google credentials server-side. All replicas must use the same PostgreSQL session store. Verify real Google sign-in and explicit linking with accounts whose ownership has been confirmed. Configure SMTP or Resend and confirm delivery of verification, subscription, and Google-only deletion codes.
6. **Verify crawler behavior.** Point each intended custom hostname at the deployment and provision HTTPS through the host. In Settings, save the hostname and publish the generated TXT record at `_incblog-verification.<hostname>`. Verify DNS ownership before designating the domain canonical. Legacy custom hostnames start unverified. A verified host that is still an alias serves a disallowing robots response and redirects its sitemap to the canonical platform feed. The platform sitemap index lists platform blogs with public posts. A canonical custom domain serves a same-host sitemap. Check the actual site with Search Console or a crawler, including share-image fetches, old-slug responses, robots, and XML.

Run `npm run typecheck`, the full Jest suite, and `npm audit --omit=dev` before rollout. Type checking covers the SEO URL, route-input, context, and metadata contracts while the application remains JavaScript.
